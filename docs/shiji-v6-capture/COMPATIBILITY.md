# 数据兼容、迁移与回退

## 存储边界

任务写入既有 `library.sqlite3` 的两张可选本机表：`capture_jobs` 与 `capture_control`。没有新建并行收藏库，没有修改资源／附件交换字段，`PRAGMA user_version` 仍为 3，ZIP manifest 仍为 2，Mac ↔ iPhone 协议不变。

`capture_jobs` 保存稳定 ID、resource_id、kind（capture／preview／asset）、规范化 URL、入队版本 resource_version、提交预期版本 expected_revision、状态、尝试次数、下次重试时间、安全错误摘要、时间戳、租约、建议／审核状态及任务选项。唯一键为 resource_id＋URL＋类型＋入队版本＋规范选项摘要，防止同一逻辑任务重复创建。索引覆盖待执行任务和资源关联；`capture_control` 保存暂停与租约 generation。

这些表是**本机派生工作状态**，不成为资源权威数据。JSON 导出、iPhone 同步和 manifest 资源交换均不携带它们。SQLite 快照自然包含原始可选表；现有 manifest 恢复流程重新建立资源与附件，不信任／导入快照中的任务、租约和凭据。

## 启动迁移

1. Store 在原有初始化中使用 `CREATE TABLE/INDEX IF NOT EXISTS` 增加可选结构，不重写现有资源行。
2. 恢复已经过期的 running 租约；保留尚有效租约，防止双进程抢占。
3. 旧资源不会仅因打开新版本而全部入队。新网站／URL 变更和明确采集会创建任务；JSON／书签导入的新增资源经过既有 Store 写入路径。历史无封面预览仍需用户启用原有默认关闭开关。
4. 新资源和入队在同一事务中，任务插入失败时资源保存也回滚。网络不参与这一事务。

旧 schema-3 数据库、旧 JSON、旧 manifest-2 ZIP 继续可读。实际测试覆盖升级打开、ZIP 真字节恢复、桌面交换、Swift 核心与真实 HTTPS 双向同步。旧 App 忽略额外表，但不会推进 V6 队列。

## 回退步骤

回退应在退出所有访问该资源库的 App／后端之后进行，并保留一份用户认可的完整备份。可直接运行原 Next 候选版本，额外任务表不会改变其资源读取。若确定丢弃本机任务历史，可在**已确认的副本**中删除 `capture_jobs` 与 `capture_control`，不删除资源、附件、settings 或配对数据。重新安装 V6 会重建空任务表；不会静默重新发送历史收藏。

这里没有自动执行任何正式库回退／删除命令。测试只使用临时数据库、附件和随机端口。

## 并发与附件恢复

- 取消／暂停／删除撤销租约。删除后再撤销删除，也不能使旧网络响应重新获得写入权限。
- 手工标题、分类、标签、备注、URL、封面等任何资源版本变更均使旧响应过期；重试不能越过版本保护。
- 发布附件、选择封面和任务完成在同一数据库事务内；提交异常清理本次新发布文件，不清理已有复用文件。
- 非封面 asset 新增也会置 dirty、推进既有快照变更代数，防止自动恢复快照漏掉附件。
- 文件系统与 SQLite 没有跨文件 ACID：在文件发布后、事务提交前强杀进程，仍可能留下未引用文件。当前 100 URL 中断测试没有发现孤儿附件，但不构成所有崩溃切点证明。既有附件健康检查保留，后续可增加该切点的专项注入测试。

## 后续集成边界

Search 2.0 的 FTS／中文索引应是可重建本机派生数据，不能混入同步权威字段；先保护完整选择、过滤、智能集合和冲突语义，再改为服务端按需查询。

Cover Studio 的用户变体偏好属于用户内容，不能直接借用本机任务表保存并假装已同步。应另提资源兼容方案，覆盖 Swift App Group JSON、旧导入、manifest、冲突与真实封面优先级，获得批准后实施。本轮不引入这些字段，也不改变 V5 美术模板。
