# Cover preferences: data and recovery contract

- Authoritative preference: optional `coverConfig` in the existing resource JSON payload. The selected attachment remains the existing `coverId`. No new resource model, SQLite authority table, worker, cloud API or third-party runtime dependency.
- SQLite `user_version=3`, ZIP manifest2, iPhone App Group JSON and HTTPS sync protocol1 remain unchanged. Search indexes and gallery caches remain derived data. Browser localStorage stores existing display modes, never authoritative cover preferences.
- Initialization: old resources without preferences are automatic and are not rewritten just to add defaults. A saved version1 preference is normalized to bounded defaults. Explicit null resets to automatic; it is retained as a tombstone during exchange. Missing/null compare semantically equal for sync conflict detection.
- Rollback: checking out the previous client keeps the optional JSON property and attachment reference. Old partial writers that omit the property preserve the existing preference. Old renderers may ignore the preference. Preferences are not deleted by rolling back application code. Full JSON import without attachment bytes intentionally falls back to artwork.
- Unknown bounded keys round-trip; future versions remain opaque. Renderers fall back to original V5 and editors protect the future object except for explicit reset. Bounds: 8KiB JSON, nesting4, finite numbers, valid Unicode, enum/type and hex-color validation. Cover text does not replace the original title, notes, classification or tags.
- Atomic save: compare config/coverId field baselines under the existing Store lock or AppGroup coordinator. Unrelated edits merge; conflicting cover edits return409 / a native conflict error. Input image verification runs outside the write lock. Selected/uploaded images and config publish in the same business operation; ordinary failure removes newly published bytes. Same-resource verified hashes reuse existing attachments. Identical retries are idempotent.
- Desktop uncertain outcomes: fetch actual persisted state, compare config/image hash, then either accept the confirmed save or retain the original draft/baseline for retry. Save ownership extends through asynchronous presentation refresh. Cancelled uploads never reach the API. Late file reads cannot mutate a reopened draft.
- Source policy is the same in draft and saved display: manual/local selection and Auto may use a pending upload; Website and Poster never get shadowed by it. Real image decode failure shows the existing artwork and a truthful editor status. Selecting Poster keeps the real bytes and coverId intact.
- Backups: tests use actual ZIP export/restore, including colliding attachment-ID remapping; no nested attachment ID bypasses existing remapping. Native tests exchange actual ZIP bytes with the desktop Store and validate both directions. HTTPS tests use disposable credentials/certificates and existing conflict/TLS protections. Late capture-job writes do not overwrite cover preferences.

All validation uses temporary directories, random local ports and disposable credentials. No production library or actual pairing record was read or modified. The existing ZIP resource-count safety limit is not increased; 50K rendering tests do not certify a 50K ZIP archive.
