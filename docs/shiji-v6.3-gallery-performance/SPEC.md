## 四、核心任务二：实现高质量画廊窗口化

V6.2 已经支持服务端分页，但前端加载更多资源时，已加载卡片仍持续累积在 DOM 中。

目前已观察到：

- 1020 张累计卡片时存在明显长帧
- 最后一批渲染约 230ms
- 混合压力样本出现约 933ms 最大帧间隔

需要设计真正的 DOM Windowing / Virtualization。

核心目标：

**资源可以持续向下浏览，但 DOM 中不需要永久保留所有已经离开视口的卡片。**

要求：

1. 根据视口和 overscan 范围决定实际挂载卡片。
2. 保留资源顺序和稳定 ID。
3. 支持不同高度、不同宽度的海报卡片。
4. 支持响应式三列、双列、单列。
5. 离开视口的卡片可以卸载。
6. 重新进入视口时可靠恢复。
7. 使用必要的高度缓存或占位机制。
8. 避免滚动跳动、布局突然改变和内容闪烁。
9. 窗口尺寸变化后正确重新计算布局。
10. 与现有服务器分页协同工作。

不能使用只能处理固定高度普通列表的简单方案，除非能证明它完整支持现有视觉布局。

不要引入第二套资源状态模型。

优先复用现有卡片 reconciliation 和 Motion 系统。

对于真实测量证明无法安全窗口化的特殊场景，可使用局部保留或独立展示层，但不得默默牺牲交互正确性。

## 七、核心任务五：优化宽泛搜索与前端更新

V6.2 已实现全文索引，但真实浏览器中仍观察到宽泛查询输入到呈现约 1 秒的延迟。

需要分离测量：

- 输入防抖
- 网络请求
- SQLite 搜索
- JSON 编码与传输
- JS 解析
- 状态更新
- DOM reconciliation
- 样式计算
- 实际画面呈现

找出真实瓶颈，实施针对性优化。

可以考虑：

- 减少不必要的全局 render
- 更细粒度的 DOM 更新
- 搜索结果缓存和版本失效
- 减少重复构建卡片 HTML
- 分离画廊和 Hero 的更新
- 稳定计算项目、标签和分类计数
- 降低重复布局读取
- 避免每次输入都重新扫描整个已加载 DOM
- 更合理的索引准备与可见状态反馈

保留现有服务端查询正确性，不以降低结果数量或牺牲排序精度冒充速度提升。

重点比较：

1. DOM 卡片峰值数量

3. 长任务数量

5. rAF P50 / P95 / Max
6. 用户输入到结果呈现的端到端延迟

8. 原生 WebContent 内存
9. CPU 使用情况

建议目标：

- DOM 卡片数量不再随浏览总量无限增长
- 1020+ 卡片累计浏览时明显减少长帧
- 搜索与切换分类尽量保持及时响应
- 不引入新的点击、焦点或选择错误
- 保留 V5 的原始视觉完成度

这些是优化目标，不是可提前宣称达到的测试结果。
